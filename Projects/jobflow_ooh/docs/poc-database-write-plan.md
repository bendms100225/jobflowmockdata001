# POC database write plan

This plan covers experimental inserts into the standalone `JobFlowDemo` database on `localhost\SQLEXPRESS`. The database is disposable and is not connected to hosted JobFlow. The writer is not production-safe and is not supplier-supported. Do not point it at any other database.

## Gate

`ExperimentalDirectSqlJobFlowJobWriter` is registered only when all of these are true:

- `ASPNETCORE_ENVIRONMENT` is `Development`
- `JobFlowWrites:Mode` is `ExperimentalDirectSql`
- `JobFlowWrites:AllowDevelopmentDatabaseMutation` is true
- `ConnectionStrings:JobFlowExperimental` uses database name `JobFlowDemo` and does not set `ApplicationIntent=ReadOnly`

The process refuses to start, and `CreateAsync` throws, if experimental mode is combined with any other database name or with a non-development environment. The default mode in `appsettings.json` remains `Disabled`.

## Before the first write

A full backup was taken and verified before any experimental insert. The file, restore command, and baseline counts are in `docs/poc-database-restore.md`.

## What is written

One transaction inserts:

1. `dbo.orders`, with `jobno` generated by the identity column (`OUTPUT INSERTED.jobno`)
2. `dbo.selectsection`, linked to that `jobno` and an existing `sscode`
3. `dbo.userlog`, with `formname` `ORDER`, `luser` equal to the configured JobFlow login, and `ldate` set to the London time of the insert

The transaction then reads those three rows back. It commits only when the job number, client, site, category, order reference, description marker, deadline, section link, and order log all match. Any failure rolls the transaction back. The UI shows `The experimental job was not created. The database transaction was rolled back.` SQL identity values are not returned to the previous number after a rollback; the orders row itself is not kept.

Existing JobFlow rows are not updated or deleted by the application. The web UI has no delete action.

## What is not written

These tables stay untouched:

- `dbo.status`
- `dbo.jobplan`
- `dbo.allocation`

The selected engineer is not stored in JobFlow. The result page says `Requested engineer, not yet assigned in JobFlow`. Project manager, coordinator, and margin (`pmanager`, `pcodinator`, `profitper`) are left null. No OOH section or subsection row is created.

## Markers

Application jobs use description prefix `POC-OOH-` and order prefix `POC-`. Automated tests use `POC-OOH-TEST-` and `POC-TEST-`. The recent screen lists the application marker and hides the test marker. Ordinary historical jobs are excluded by both filters.

## Idempotency

Repeated submits are stored in `JobFlowOohPortal.dbo.PocIdempotency`, which is not a JobFlow vendor table. The same key and the same content return the original job number. The same key with different content is rejected. The portal database is created by `PortalDatabaseInitializer`. No column is added to a JobFlow table.

## Login and job type

`DevelopmentUsername` and `DevelopmentCallTakenBy` come from user-secrets and must already exist in `dbo.loginuser`. They are not hard-coded. `DevelopmentJobType` must already occur on `dbo.orders`. The stored number is shown only under development diagnostics. It is not labelled Reactive.

## Cleanup

`scripts/poc-cleanup-job.sql` can remove one marked job. It rolls back unless `@Commit` is set to 1. Restoring the pre-write backup is the preferred reset.
